# Build security implementation

This is the executable intake for [CR-0013](../../docs/change-requests/CR-0013-build-security-pipeline.md) and its [ToDo](../../docs/todos/CR-0013-build-security-pipeline.md), covering OPS-10 and the protected-CI part of OPS-12. The [delivery guide](../../AGENTS.md#verification-and-release-evidence) and [deployment design](../../docs/design/deployment-and-operations.md#build-security-and-cve-gate) still define release requirements. A local green unit test is evidence for the validator, not proof that any image has been scanned or approved.

## Pull requests

`.github/workflows/pr-checks.yml` runs `make check`, deterministic tests, Ruff lint, mypy on implementation modules, secret scanning, a separate configuration scan, and exact-lock CVE/KEV scans. It runs with read-only repository permission and no enterprise or model secrets. Trivy v0.76.1 and every GitHub action are pinned. The Python 3.13 tooling set is frozen in `requirements-dev.lock` with exact versions; the spike worker lock is `spikes/full_graph/requirements-worker.lock` and must also carry a SHA-256 hash for every package because its Dockerfile installs with `pip --require-hashes`. `make lockcheck` compares every direct `requirements-dev.txt` numeric range with its exact lock pin, and compares the five reviewed direct worker pins and version-manifest claims with the worker hash lock. Unsupported development requirement syntax fails closed until reviewed. Trivy recognizes `requirements.txt`, so the scanner copies each lock to that basename in an isolated temporary directory. Validation requires exactly one `requirements.txt` result with `Class=lang-pkgs`, `Type=pip`, and the exact normalized locked package/version set. Wrong ecosystems, extra packages, and zero-package results fail. This follows [Trivy's Python coverage guidance](https://trivy.dev/docs/latest/guide/coverage/language/python/).

Protected branch rules must require all four PR jobs. The repository workflow alone cannot turn a status into a merge block.

## Exact image promotion and daily rescan

Copy [the example manifest](release-manifest.example.json) to `release-manifest.json` **only after** every actual image reference has been resolved to its final registry digest and each role's deployed `linux/amd64` or `linux/arm64` platform is known. The spike worker is fixed to `linux/arm64`, matching its current resolved lock. The manifest must explicitly set `gcp_host_relay_enabled: false`: the optional host GCP adapter has no qualified resolved host lock or endpoint and remains disabled. The manual workflow accepts only a full `refs/heads/<default branch>` ref, including when a tag has the branch's short name. Its daily schedule scans `deployed-manifest.json`, which must enumerate the digests and platforms actually deployed. Both files are intentionally absent now: candidate promotion and deployed-digest qualification are blocked until the relevant manifest and evidence exist. An OpenShell Kubernetes run must set `uses_kubernetes: true` and include `agent_sandbox_controller`; every additional image actually used must also be listed. This implementation accepts only the disposable `spike` profile. Expand the profile and role checks under a reviewed CR before promoting the later application.

The scanner refreshes Trivy's vulnerability DB once, records `trivy version --format json`, then scans every image **by `repo@sha256:...` and `--platform`** with updates frozen. It writes a full JSON vulnerability report, CycloneDX SBOM, and effective-rootfs archive inventory for each digest/platform, the CISA KEV feed retrieved during the run, hashes of all evidence files and locks, and a decision summary. Validation requires a fresh DB, a scan and archive inventory no older than 24 hours, observed nonempty OS and language package classes in each image report, an exact match for every locked Python package in the final spike worker, the image config's exact OS/architecture, and an SBOM root OCI PURL with the exact digest and architecture. It compares the **multiset of package PURLs** in the scan and SBOM, including duplicates. A scan command's `--pkg-types os,library` option alone cannot prove inventory coverage. The locally inspected OpenShell runtime digest has no observed OS package class, so this gate blocks it until an independent, reviewed digest/platform-specific absence proof is added; no blanket runtime exception exists.

The CISA KEV feed must have its complete declared entry count, unique CVE IDs, and populated required entry fields. Every KEV, HIGH, CRITICAL, or UNKNOWN finding blocks without a scoped security-owner disposition. LOW and MEDIUM findings also block until a scoped owner, ticket, reason, and future due date are recorded. A separately governed `--exceptions` JSON file may carry `triage` records for lower severities or `not_affected`/`temporary_exception` records with exact digest/platform/package/version/CVE scope, security owner, vendor evidence, mitigation, approval time, and an expiry within 30 days. The checked-in workflows supply no disposition file. A string naming an approver is not independent approval proof; source ownership and the disposition file's review/access policy remain external gates.

**Archive coverage:** [Independent image review](../../docs/evidence/CR-0013-pip-removal-candidate-2026-10-26.md) found a bootstrappable `ensurepip` wheel that the ordinary package scan and SBOM missed. For each manifest image, the scanner resolves the requested immutable reference on the declared platform, creates a stopped network-disabled Docker container with a fresh nonce label/name, and exports its effective final filesystem without running image code or extracting archive contents. It removes the container only after a fresh check of the exact ID, nonce, name, image reference, network/read-only configuration, and `created`/not-running state. A stdout/CID mismatch or uncertain ownership leaves the gate failed for manual reconciliation; cleanup never uses `--force`.

The schema-v2 inventory records the requested digest/platform, Docker's observed image ID, platform child descriptor, container image ID, ordered rootfs diff IDs, full export hash and entry counts, and candidate file paths/hashes. These image identifiers can differ for a multi-platform index. The release validator requires a fresh, complete, checksummed inventory and matches Trivy's `Metadata.ImageID` and ordered `DiffIDs`/image-config rootfs diff IDs to Docker's container image ID and rootfs diff IDs. It also requires the Trivy 0.76.1 CycloneDX **root component** to have exactly one matching `aquasecurity:trivy:ImageID` and a complete matching multiset of `aquasecurity:trivy:DiffID` properties. Trivy sorts these SBOM properties, so the scan-to-Docker comparison remains ordered while the SBOM comparison uses a multiset; missing, malformed, duplicate, or extra identity properties block release. The gate rejects any installable archive, ZIP under an unexpected filename, or file/link beneath an explicit vendor tree. Ordinary installed `.dist-info/METADATA` outside a vendor tree remains part of normal Trivy package reconciliation. The first gate has **no retained-archive or vendor-tree disposition path**; a candidate remains blocked until a separately reviewed exact-digest content-scan/disposition path exists. The effective [Docker export](https://docs.docker.com/reference/cli/docker/container/export/) excludes bytes hidden by image-layer whiteouts; it is not an all-layer forensic scan.

The [schema-v2 local worker inventory](../../docs/evidence/CR-0013-final-rootfs-archive-inventory-v2-2026-10-26.json) found **21 unpacked vendor files** in the corrected worker (`anthropic/_vendor` and `openai/_vendor`), so that digest remains blocked even though Trivy/Docker image and layer identities match. The [CycloneDX root correction evidence](../../docs/evidence/CR-0013-sbom-root-identity-correction-2026-10-26.md) records the red/green gate cases and the same image's matching cached SBOM properties. The worker also retains 44 unresolved Debian HIGH findings. This implementation advances [CR-0013](../../docs/change-requests/CR-0013-build-security-pipeline.md) / [ToDo](../../docs/todos/CR-0013-build-security-pipeline.md) but does not qualify other images, protected CI, or security-owner disposition.

Scan JSON accepts an omitted or null `Vulnerabilities` list on a clean Trivy result and an omitted or null `VendorIDs` list on a finding. Other non-list values fail the gate, even when an adjacent evidence checksum is recomputed. This prevents malformed false values from being treated as a clean scan or as missing aliases.

Run the same scanner locally when registry and network access are approved:

```sh
python3 -m scripts.build_security.scan release \
  --manifest scripts/build_security/release-manifest.json \
  --repository-root . \
  --output /private/tmp/research-release-evidence
```

The workflow uploads evidence even when validation fails, for review. A missing manifest, lock, image digest, SBOM, scan, KEV feed, or fresh advisory DB returns a nonzero status. The scheduled job deliberately fails if no deployed manifest has been registered; that is a visible unfinished operations gate. Registry publication, runtime-inventory reconciliation, signature/admission proof, security-owner policy approval, artifact retention beyond Actions, branch protection, and a real default-branch workflow run remain necessary before promotion. See [Trivy image scanning](https://trivy.dev/docs/latest/guide/target/container_image/) and [SBOM generation](https://trivy.dev/docs/latest/guide/supply-chain/sbom/).
