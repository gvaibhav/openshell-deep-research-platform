# CR-0021/0022 proposed v3 evaluator contract — independent design review

**Date and scope:** 2026-10-26. Independent, read-only review of the proposed matched-evaluation contract before implementation, using the principal-engineer, platform-feasibility, and research-worker-evaluation skills. Requirement IDs: SEL-01, SEL-05, RES-09. Data class: synthetic/public. Boundaries reviewed: candidate output versus evaluator packet, blind quality review versus labeled control review, metric/export evidence versus signed assertions, and scorecard versus human selection. The review changed no implementation or contract file; this evidence note is its only artifact.

**Verdict:** The direction is sound, but the proposed signed-readiness handoff is **not ready for implementation as written**. One Blocker can let a signed blind review score an answer materially different from the candidate's answer. The Important findings below need specific contract rules before TDD and witnessed pilot use. CR-0021 and CR-0022 remain **Open**. There is no approved corpus, observed candidate run, independent witness receipt, or human SEL decision.

The intended case-12 behavior is coherent **if the human finding is trustworthy**: one source-exact full `github-deploy-77` citation can be named by both target findings. An unrelated quote from the same source receives zero when the blind reviewer records `supported: false`; source identity alone cannot establish semantic support. Code can verify source membership, span bytes, indices, and signatures, but cannot prove that a human semantic judgment is correct. The independent sample review and approved corpus remain necessary.

## Ranked findings

### Blocker

1. **The reviewed packet answer may differ materially from the retained candidate answer.** `docs/design/matched-evaluation-contract-v3.md:22,37` has blind reviewers judge the completed packet, while `eval/blind_review/tool.py:402-431,471-505` accepts separate `raw_answer` and `packet_answer`, hashes both, and makes the latter the reviewed answer. The v2 custody guide permits a reviewer-safe redaction at `eval/blind_review/README.md:27`; neither it nor the v3 design requires content equivalence. For example, a raw answer could give a wrong deployment time while its screened packet is edited to the correct time and cited full record. Both versions can be faithfully signed, and the support findings would describe the edited packet rather than the result being compared under SEL-01/RES-09. **Minimal correction for this wholly synthetic/public pilot:** require byte-for-byte `raw_answer == packet_answer` during packet preparation **and** signed-bundle verification. If the raw answer reveals candidate identity or out-of-view content, quarantine or defer that cell and rerun after a compliant input; do not redact its claims. Add a negative fixture with a wrong raw answer and repaired packet that cannot produce signed readiness. This rule must also close in the current CR-0011 v2 path before any observed use; v3 cannot inherit an unsafe packet preparation path. The separate control reviewer must still corroborate the raw answer against the independently retained candidate run.

### Important

2. **The reviewer target view is not a specified, independently bound projection.** `docs/design/matched-evaluation-contract-v3.md:22,26,65-66` says targets live in an evaluator workbench while the reviewer packet stays unchanged. The existing packet contains `case_id`, answer, allowed snapshots, and citations, but no targets (`eval/blind_review/tool.py:471-486`). Looking up targets directly in `eval/corpus/v1/cases.json` also exposes forbidden IDs, expected behavior, permission setup, and sentinels that the blind reviewer should not need. A free-form workbench lookup gives no proof of which target bytes the reviewer saw. **Minimal correction:** specify a deterministic reviewer-only projection keyed by approved corpus/source digests and packet case ID, containing only target index, expected permitted evidence ID, anchor/semantic target text, and the already approved visible-source context. Validate every projected ID and anchor against the packet's permitted source view, bind the projection digest in the signed blind review, and deny extra candidate labels, forbidden IDs/text, control claims, or stale target bytes. Keep the full corpus in separate evaluator custody. Test the positive case-12 view and leak/stale-projection negatives.

3. **Cost coverage and the readiness consequence of unknown cost are ambiguous.** `docs/design/matched-evaluation-contract-v3.md:43-53` correctly distinguishes observed zero from unavailable and proposes an observed subtotal, but only explicitly nulls `total_cost_usd` when a **completed** cell has unavailable cost. With 23 completed observed-cost cases and one deferred case, a numeric `total_cost_usd` could still be mistaken for the full 24-case cost. The design also leaves the v5 machine-state/required-human-disposition rule implicit (`docs/todos/CR-0022-observed-cost-and-report-export.md:19-20`). **Minimal correction:** define per-candidate counts for required, completed, observed-cost, unavailable-cost, deferred, failed, and missing cells; label the sum of measured completed cells `observed_subtotal_usd`; set `total_cost_usd` to null unless every required cell completed **and** every cost was observed. State whether `ready_for_human_decision` may coexist with unavailable cost and, if so, require an explicit unresolved-cost flag and a separate signed/owned human uncertainty or estimate disposition before SEL. Test partial matrix, unknown, and measured zero separately. No estimate may enter an observed field.

4. **Report-export semantics do not cover every completed behavior or prove the exported object is the reviewed report.** `docs/design/matched-evaluation-contract-v3.md:55` lists five states for answers/abstentions, then permits `not_applicable` on a denied-source cell without defining whether all completed cells require the field, which denials qualify, or how expected/observed behavior mismatches are handled. An arbitrary retained file plus SHA-256 and an attempt reference can satisfy the prose without proving that the product exported the case's answer and citations. This affects SEL-01 and can hide a denied-source export. **Minimal correction:** require exactly one `report_export` on every completed cell and specify a small truth table: ordinary answer/abstention uses an actual attempt outcome; `not_applicable` is permitted only for a correctly denied expected-denial cell; an unexpected denial is a quality failure and cannot masquerade as successful export; an unauthorized answer/export is a control violation, with its incident evidence retained safely. For `exported`, bind the actual product export method/time, format, artifact bytes, and independently checked answer/citation correspondence to that run. Count eligible export cells separately from justified denied-source N/A cells. Add positive abstention export and negative empty/wrong-artifact, unexpected-denial, and private-denial-export fixtures.

5. **The metric/export control attestation lacks a field-level source-of-truth contract.** `docs/design/matched-evaluation-contract-v3.md:46-55` supplies evidence refs and hashes and mentions a distinct corroboration record, but does not define its per-cell keys, reviewer decision, measurement basis, export-event comparison, or how that decision is bound into control review v3 and witness v4. A hash identifies supplied bytes; it does not show that a provider bill reports `$0.00`, that per-case usage is unavailable, or that a product generated an exported report. `docs/change-requests/CR-0022-observed-cost-and-report-export.md:20,25` promises observed provenance and denial of false export, so this is an implementation handoff gap. **Minimal correction:** define one control-reviewed record per completed `(candidate_id, case_id, run_id)` that compares the exact raw/candidate cost and export objects to independently retained billing/usage and product-export evidence, records `corroborated` or a blocking reason, and binds its digest to the signed control review and witness receipt. Include the cost measurement window/allocation basis and export artifact content check. A self-asserted ref, missing independent evidence, changed amount, or changed export bytes must deny signed readiness. This can be a typed section of control review v3 rather than another signing service.

6. **The migration and human handoffs give conflicting version instructions.** The impact matrix says evaluator case and binding schemas need versioned new shapes (`docs/feasibility-and-market-assessment.md:229`), and CR-0021 says to version the binding schema (`docs/change-requests/CR-0021-citation-support-fairness.md:29`), while the detailed table retains corpus v1 and scorer-binding v2 unchanged (`docs/design/matched-evaluation-contract-v3.md:61-70`). Keeping the path catalog v2 is reasonable if the verifier rejects legacy referenced artifacts, but the documents need one rule. The affected decision template still requests a **v3** scorecard, exact citation spans, and only observed case cost, with no export outcome or unavailable-cost disposition (`eval/decision-record-template.md:28`); the blind custody guide still describes only the v2 review (`eval/blind_review/README.md:3,80,89`). **Minimal correction:** reconcile the impact/CR language with the exact migration table; state that unchanged catalog/packet shapes are location/view plumbing while the verifier pins the new artifact versions and rejects mixed bundles. Mark current v2 guide sections as current and link the proposed v3 obligations. Update the human template now with proposed scorecard v5, target findings, observed-subtotal/unknown counts, export outcome and evidence, and explicit human uncertainty disposition, without claiming those fields exist today. Retain the complete candidate×case freeze and regenerate/re-sign the whole approved matrix; do not upgrade a partial signed bundle in place.

### Optional

7. **Keep the migration small and distinguish red tests from guard tests.** `docs/design/matched-evaluation-contract-v3.md:67-69,87` can meet the requirements by adding support findings to the already signed blind review and metric/export corroboration to the already signed control review, then bumping artifact versions that carry new bytes. A new separately signed metric service is unnecessary. The current v2 scorer already rejects an unrelated same-source quote through exact-anchor equality (`eval/scorecard.py:923-928`), so that negative fixture is a **regression guard**, while the case-12 full-document acceptance is the failing red test. Phrase the TDD gate accordingly; retain both fixtures.
