## Important finding: CycloneDX root identity is not bound to the exported child

[gate.py:466-500](../../scripts/build_security/gate.py#L466-L500) checks the SBOM's requested OCI digest, architecture, and library PURLs, and [gate.py:693-710](../../scripts/build_security/gate.py#L693-L710) binds the **vulnerability report** to the Docker inventory's image ID and ordered rootfs diff IDs. It does not check the Trivy CycloneDX root component's `aquasecurity:trivy:ImageID` and `aquasecurity:trivy:DiffID` properties. The clean synthetic release fixture has those root properties **absent** and passes. After adding a well-formed but wrong SBOM `ImageID=sha256:aaaa…` and `DiffID=sha256:bbbb…`, and recomputing its evidence checksum, `validate_release()` still returned `blocking_findings=0`. A separate SBOM scan may therefore describe another child with the same requested multi-platform index/platform and package PURLs while the vulnerability scan and archive inventory agree with each other. The [deployment design](../design/deployment-and-operations.md#build-security-and-cve-gate) calls for binding inventory child/config/rootfs identities to the scan **and SBOM**.

For pinned Trivy 0.76.1, require its SBOM root `ImageID` to equal the scan/inventory image ID and require the SBOM root DiffID multiset to match the inventory/scan layer set; the observed CycloneDX properties are sorted rather than in filesystem layer order. Preserve the existing ordered scan-to-Docker DiffID equality, and fail if the SBOM properties are missing, malformed, duplicated unexpectedly, or inconsistent. Add absent/wrong root-property denial tests and a positive test using the observed Trivy 0.76.1 shape. This is a release evidence-integrity gap, not a finding that the locally inspected worker's actual SBOM is mismatched: its observed root properties agree with its scan and inventory.
