## Findings

### Blocker — cleanup can force-remove a container the scan did not create

[archive_inventory.py:314-340](../../scripts/build_security/archive_inventory.py#L314-L340) rejects a mismatch between Docker `container create` output and the CID file, but its `finally` block still prefers the CID file and issues `docker container rm --force --volumes` for that ID. In a fake-Docker reproduction, create returned `bbbb…`, the CID file held a different valid `cccc…`, and the gate denied the mismatch **after issuing a force-removal for `cccc…`**. That ID could belong to an unrelated running container; the `--force --volumes` option makes the failure destructive. A CID file's syntax and presence do not prove ownership. Use a unique per-create nonce label/name, verify the candidate ID's label, image, stopped state, and create intent before cleanup, and never force-remove an unverified or running ID. On an identity mismatch, fail the gate and leave an uncertain container for controlled reconciliation. Add a red/green test asserting that the mismatched CID is never removed.

### Important — unpacked vendored components can produce a clean inventory

[_candidate_reason at archive_inventory.py:68-82](../../scripts/build_security/archive_inventory.py#L68-L82) recognizes selected manifest names only. A synthetic export containing `opt/app/_vendor/bom.cdx.json` (the manifest format observed inside the prior pip wheel) and `opt/app/_vendor/urllib3/__init__.py` returned `regular_files_seen=2, candidates=[]`. The release validator therefore has no candidate to reject. This undercuts the [CR acceptance](../change-requests/CR-0013-build-security-pipeline.md) that a final-filesystem inventory proves no unscanned vendored code remains. At minimum recognize CycloneDX/SPDX manifest names and add a negative fixture for unpacked vendored code without a listed manifest. A conservative vendor-directory/code inventory, or an explicit independently scanned/dispositioned vendor tree, is needed before claiming vendored-code coverage. Keep the current no-retained-candidate policy until a reviewed content-scan disposition format exists.

### Important — the validator does not bind inventory identity to the scan's image identity

[gate.py:503-574](../../scripts/build_security/gate.py#L503-L574) validates the inventory's observed IDs as SHA-256-shaped strings, and [gate.py:628-676](../../scripts/build_security/gate.py#L628-L676) validates scan/SBOM and inventory separately. It does not compare the inventory's `container_image_id`, resolved child identity, or rootfs layer identity with the scan's `Metadata.ImageID` or package-observed child. In a synthetic full-release fixture, scan `Metadata.ImageID=sha256:aaaa…`, inventory `container_image_id=sha256:bbbb…`, `resolved_image_id=sha256:cccc…`, and `resolved_descriptor_digest=sha256:dddd…` passed `validate_release()` with `blocking_findings=0` after evidence checksums were updated. The producer's [capture_image_inventory](../../scripts/build_security/archive_inventory.py#L292-L354) checks its own Docker create/inspect path, but the consuming gate has no cross-artifact equality proof that Trivy and Docker observed the same child of a multi-platform reference. Record a child/config/rootfs identity in both observations and fail on mismatch; add a denial test with well-formed but unequal identities. A local checksum proves that a JSON file was not changed after its evidence manifest was written, not that two scanner observations covered one child image.
