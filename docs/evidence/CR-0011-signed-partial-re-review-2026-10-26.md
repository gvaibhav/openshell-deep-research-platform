## Blocker: a switched binding catalog can place a ready report in the reviewed packet directory

[The CLI](../../eval/scorecard.py) calls `_consumed_output_paths` before scoring and again before publication (lines 1584–1609), but [the binding verifier](../../eval/binding.py) separately reads the untrusted path catalog at line 89. The final output exclusion checks the first and third catalog snapshots, **not necessarily the packet directory actually used by signature verification**. A clean packet directory passes the verifier's exact-file check before publication.

I reproduced this with a valid, signed 3-candidate × 20-case synthetic fixture and an exact copy of its packet directory. A deterministic catalog-read hook returned original directory **A** during output preflight, copied directory **B** during signed verification, then **A** during output postflight. With `--output B/scorecard.json`, the CLI returned **0**, wrote a `ready_for_human_decision` scorecard **inside B**, and reported no error. B was the directory whose packet bytes the scorer had just verified. This can expose concealed candidate labels and run metadata if the packet directory is shared with blind reviewers, violating the review trust boundary. The hook models a concurrent change to the mutable catalog; the test did not alter repository files.

**Required fix and deny proof:** Retain the *same* verified catalog/path snapshot throughout scoring and output publication, or return the exact verified consumed paths from binding and check output against them. Fail closed if catalog bytes or resolved paths change during the invocation. Red/green a signed A → B → A switch with output under B, plus a switch that remains at B, normal fresh private output, old-path reuse, symlink, and link-race cases. Do not share a packet directory or use a scorecard produced while this boundary is open.
