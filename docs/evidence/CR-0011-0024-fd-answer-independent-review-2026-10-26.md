## Blocker 1: packet preparation can put the concealed map in the reviewer packet directory

`eval/blind_review/tool.py:565-603` checks map/packet separation by pathname before publication. `eval/blind_review/tool.py:732-741` later creates and writes packet children, manifest, and concealed map through fresh absolute path lookups. `_write_exclusive` at `eval/blind_review/tool.py:604-617` uses `O_NOFOLLOW` only on the final file. Neither output directory is held by FD and compared with the other before publication.

I reproduced two independent path switches using the approved one-cell synthetic fixture. First, `map_path=attacker/route/private/candidate-map.json` resolved to an owner-only private directory at preflight; I switched intermediate `route` just before the map file's `os.open` to a path whose `private` component linked to the newly made packet directory. Preparation returned success and wrote the concealed `candidate-map.json` **inside reviewer packets**, leaving the original private directory empty. Second, with `packet_dir=attacker/route/reviewer-packets` initially resolving to a new benign directory, I switched `route` after `mkdir` and before the first packet write to the physical parent of `map_path`. Preparation again returned success; the resolved packet directory and map parent were then the **same inode**, with anonymous packet files and the concealed map together. The true initially created benign packet directory remained empty. Both paths satisfy the initial separation checks. A controlled copy of that packet directory would reveal candidate labels before the full blind review is frozen.

**Required correction and deny proof:** Prepare both destinations through opened, no-follow directory FDs; pin and compare their physical identities and ancestry before and throughout every packet, manifest, and map publication. Do not re-resolve caller-controlled ancestors between validation and write. Red/green both map-path and packet-path A→B/A→B→A switches, including a private map next to packet files, and require no label-bearing file in any reviewer packet directory. Preserve the stable one-cell allow case and mode-0700/0600 permissions.

## Blocker 2: unblinding can publish the labeled assembly into the packet directory

`eval/blind_review/tool.py:1941-1959` excludes a packet-directory output by resolved pathname. After signed verification, `eval/blind_review/tool.py:1979-1986` checks equality with the private map parent and then invokes `_write_exclusive` on the original **absolute pathname**. An intermediate ancestor can change after these checks. The final-file `O_NOFOLLOW` does not protect it.

I used a valid, fully signed 3-candidate × 20-case fixture and output `attacker/route/private/unblinded.json`. During all preflight and signature checks, `route` pointed to the owner-only map parent. Immediately before `_write_exclusive` opened the output, I switched only `route` to a path whose `private` component linked to the verified packet directory. `verify_and_unblind` returned the labeled assembly and created `unblinded.json` **inside the packet directory**; the private map directory had no output. No signed byte changed. This is a direct pre-reveal label leak even if the scorer's packet FD is correct.

**Required correction and deny proof:** Hold the exact owner-only private output-directory FD from before verification through exclusive publication; verify its inode and ancestry remain distinct from the packet FD, and create the labeled file relative to that held FD. Deny an intermediate output-symlink switch immediately before open and a rename switch, with no labeled or temporary file in packets. Do not distribute packets after an unblind attempt until this boundary passes independent review.

## Blocker 3: failure cleanup can delete unrelated files and directories

The exception handler at `eval/blind_review/tool.py:742-747` re-resolves both original caller pathnames: it unlinks any current `map_path` and recursively deletes any current `packet_dir`. It does not prove either current inode was created by this invocation. I reproduced both destructive cases in disposable temporary directories:

- After packet `mkdir`, I switched an intermediate packet-path symlink to an unrelated directory containing a canary and a preexisting `packet-manifest.json`. The first packet write entered that directory; the manifest's exclusive-open collision raised `BlindReviewError`. Cleanup followed the switched path and **deleted the unrelated directory and canary**. The newly created packet directory at the original benign location survived.
- After creating a new map at a benign private destination, I simulated a postwrite I/O failure and switched its intermediate symlink to a different private directory with an unrelated same-name canary. Cleanup deleted the **unrelated canary** while leaving the newly created map behind.

**Required correction and deny proof:** Track only the directory and file inodes actually created by this invocation and clean them through retained FDs or an equivalent identity-checked mechanism. Never `rmtree` or `unlink` a re-resolved untrusted pathname. Red/green both switched-path failure cases; an unrelated canary must survive, and partial artifacts must be quarantined or removed only at their actual created locations.
