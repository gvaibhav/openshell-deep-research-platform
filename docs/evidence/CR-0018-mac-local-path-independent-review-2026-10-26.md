# CR-0018 Mac-local and hosted ChatGPT path — independent review

**Date and scope:** 2026-10-26. Read-only principal-engineer and official OpenAI documentation review of the user clarification that they can configure the ChatGPT app on their Mac but cannot configure the Enterprise workspace or OpenAI Platform tunnel. Requirement IDs: SEL-01, SEL-02, SEL-05, RES-09, OPS-10. Data class: synthetic/public only. Trust boundary: local desktop MCP settings and Work execution versus hosted ChatGPT custom MCP plugins/Deep Research and Platform Secure MCP Tunnel. No tenant connection, model call, approved case packet, or secret was used. The reviewed baseline is the current CR-0018/ToDo and related design/runbook, not a deployed integration.

## Findings

1. **Important — explicitly gate the local trial on Work entitlement and effective enterprise MCP policy.** `docs/design/chatgpt-enterprise-integration.md:13`, `eval/mcp_fixture/README.md:92-94`, and `docs/todos/CR-0018-chatgpt-synthetic-mcp-baseline.md:15` permit a Mac-local trial after data approval and app configuration, but do not plainly require that this user's **Local Work** mode is enabled and that the enterprise/device MCP policy allows this specific server. OpenAI's [desktop MCP guide](https://learn.chatgpt.com/docs/extend/mcp) describes Settings > MCP servers for the shared local Codex host; it also says enterprise `mcp_servers` requirements apply to local executors. [Work availability](https://learn.chatgpt.com/docs/use-chatgpt) depends on the account/workspace, and [enterprise local-access controls](https://learn.chatgpt.com/docs/enterprise/cloud-local-access) can constrain local execution through MDM and Agent Security. Mac administrator access or a visible MCP setting does not override those controls or prove that the user's Deep Research task can select the server. **Fix:** Make the optional local branch conditional on the intended Enterprise workspace, actual Work Local entitlement, effective enterprise/device MCP allowance, and an observed Work-mode `search`/`fetch` transcript. If a Codex chat sees the server but Work does not, record a Codex-only protocol observation outside the ChatGPT baseline. A local tool call never satisfies the hosted Deep Research/source-permission gate.

2. **Important — qualify the absolute loopback statement.** `docs/change-requests/CR-0018-chatgpt-synthetic-mcp-baseline.md:18` says ChatGPT cannot reach a local fixture server directly, while the same CR later proposes a desktop STDIO connection. [OpenAI's MCP guide](https://learn.chatgpt.com/docs/extend/mcp) distinguishes hosted Work/web plugins from local desktop/Codex-host servers; [Work's local mode](https://learn.chatgpt.com/docs/use-chatgpt) can run permitted tools on the computer. **Fix:** Say the **hosted** Enterprise Deep Research/Work environment cannot reach this Mac's loopback fixture without an approved reachable endpoint or tunnel; an eligible local desktop executor may start the approved fixture over STDIO. The OpenShell gateway is not a ChatGPT source in either branch.

## Correct boundaries already stated

The CR, README, and feasibility matrix keep any local Mac MCP call as a separate compatibility observation, mark no connector approved, and defer hosted MCP/permission scoring. That distinction is supported by [hosted custom MCP access](https://developers.openai.com/api/docs/guides/custom-mcp-server), which is subject to workspace permissions, and [Secure MCP Tunnel permissions](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels), which separately require Platform tunnel roles and association with the target workspace. [Enterprise plugin controls](https://learn.chatgpt.com/docs/enterprise/apps-and-connectors) also gate plugin/app availability and actions by workspace role; local OS privileges do not grant them. The [Deep Research Work guide](https://learn.chatgpt.com/docs/web-search) says the feature depends on account/workspace availability. The cited pages do not establish that a desktop-configured MCP is selectable by this user's Deep Research workflow; only a live same-workflow transcript can establish that.

## Next-stage disposition and unrun gates

The revised documentation can support a **conditional local compatibility test**, once exact synthetic bytes, destination, and independent manifest pin receive the project-required approval. It cannot support a matched Enterprise MCP result. Record Mac app version, selected Enterprise workspace, Local Work mode and policy allowance, discovered tools, one allowed and one forbidden call, and whether the actual Deep Research workflow selected the same server. If local Work or MCP is unavailable, label that branch unavailable rather than a failed candidate.

Hosted scoring still needs an authorized workspace owner to permit the custom MCP app for the tester, an approved reachable endpoint or a Platform owner/RBAC administrator to grant Tunnels Read + Manage for creation and Read + Use for runtime/app selection, target workspace association, an approved tunnel-client artifact and runtime-key reference, and observed Deep Research source/tool/citation transcripts. [OpenAI's tunnel guide](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) states these distinct permissions and associations. The repository's human product/security corpus approval, unresolved inspected tunnel-client finding, source-parity and raw-run corroboration also remain open. Do not distribute draft case packets, expose the OpenShell gateway, or mark local/hosted MCP and source-permission cases passed until their own gates pass.
