## Current and target behavior

**Permission clarification (2026-10-26):** The user has administrator control over the ChatGPT app on their Mac and will run the 24 cases, but cannot configure the server-side Enterprise workspace or OpenAI Platform tunnel. No connector is approved. A Mac-local MCP trial is a separate compatibility observation; it does not authorize the hosted Enterprise Deep Research source. [OpenAI's desktop MCP instructions](https://learn.chatgpt.com/docs/extend/mcp) and [tunnel permission model](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) distinguish these controls. The hosted app/tunnel path remains conditional on a workspace-authorized app creator and tester use permission, plus Platform tunnel owners who grant Tunnels Read + Use to the creator selecting the tunnel and any separate runtime operator; the [owner handoff](../handoffs/chatgpt-mcp-admin-request.md) lists their exact nonsecret actions and return evidence.

The [independent Mac-path documentation review](../evidence/CR-0018-mac-local-path-independent-review-2026-10-26.md) also requires observed Work Local entitlement, effective enterprise/device MCP permission, and a Work-mode tool transcript before crediting even the local compatibility trial. Mac administrator access does not satisfy those gates.

The organization has ChatGPT Enterprise; custom read-only MCP apps and an associated OpenAI Platform Secure MCP Tunnel were reported as available capabilities, but the user lacks the server-side configuration role and **no connector is approved yet**. The user will run the 24 synthetic ChatGPT cases. The **hosted** ChatGPT Enterprise/Deep Research environment cannot reach this Mac's loopback OpenShell gateway or local fixture server directly; it needs an approved reachable endpoint or tunnel for the fixture. An eligible local desktop executor can start an approved fixture over STDIO. The gateway is **not** a ChatGPT source and need not be exposed. A runnable **local synthetic** `search`/`fetch` MCP fixture now exists; no actual tunnel, tenant discovery, or ChatGPT baseline has been observed. [Initial independent tester-packet review](../evidence/CR-0018-tester-packet-independent-review-2026-10-26.md) found self-rehashed approval and missing safe-question export; follow-up review reproduced partial output after an interrupted two-file write, duplicate case IDs in the approval schema, and evaluation schemas omitted from `make check`. Local TDD corrections require an externally registered manifest digest, exact 24-case membership, and one fresh atomically published question/projection packet directory. [Targeted re-review](../evidence/CR-0018-packet-correction-re-review-2026-10-26.md) found no remaining Blocker or Important within the operator-only parent assumption. The fixture is **not approved for tester distribution** until the external approval and custody gates pass.

Build a disposable, read-only synthetic MCP fixture server that exposes only the source IDs approved for one declared evaluation case, with exact bounded `search` and `fetch` outputs and explicit forbidden-ID denial. Prefer an [OpenAI Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) from a host that can run the fixture server, using outbound HTTPS and a separate Platform tunnel runtime key. An approved public HTTPS MCP endpoint is a fallback if the tunnel is unavailable. A file-upload baseline remains valid for research quality, but it does **not** prove MCP or source-permission behavior. The ChatGPT app must actually appear as a Deep Research source in this tenant before its MCP behavior is scored; [OpenAI notes app availability varies by workspace and app](https://help.openai.com/en/articles/10500283-deep-research-in-chatgpt).

Before either file-upload quality sharing or a tenant tunnel, a versioned `approval-manifest/v1` held under independent product/security review must bind the exact approved corpus/source/rubric byte digests, data-use destination, **each** `case-01` through `case-24` exactly once, and each case's question and allowed projection byte digests. The operator supplies the **approved manifest SHA-256 from a separate trusted register**; recomputing a replacement hash from edited local files is not approval. The projector checks approved input status and these pins, stages only the one-case `question.txt` and `projection.json`, verifies their exact bytes, and publishes them together under a fresh `--packet-dir`. Approved mode refuses the old independent `--output`/`--question-output` form; `--output` is limited to visibly non-distributable draft mode. The server independently checks the same manifest pin and case projection before serving it. Default distribution fails closed **against the unchanged, independently registered manifest digest**. Wrong case, pending approval, changed source/rubric/corpus, self-rehashed forbidden source under that unchanged pin, or a failed write leaves no final packet directory. A caller-supplied new digest is not proof of independent approval. The packet parent must be operator-only with no concurrent writers: portable directory rename does not provide an exclusive no-replace guarantee against a racing writer. No approved manifest or trusted register entry exists yet.

The first local implementation pins Python-standard-library stdio JSON-RPC and legacy MCP `2025-06-18` and `2025-11-25` (`initialize`, `notifications/initialized`, `tools/list`, `tools/call`). The older version supports a local MCP SDK 1.22.0 client, which is supplemental test tooling outside the fixture runtime/lock. Its `server/discover` response identifies a legacy server so a current client may fall back under [MCP 2026-07-28 versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning). Projection and server admission enforce common exact byte bounds and source-ID grammar; malformed Unicode must fail as a bounded RPC without ending the process. The [local v0.0.18 in-memory tunnel-client probe](../evidence/CR-0018-local-tunnel-client-proxy-2026-10-26.md) negotiated `2025-11-25`, listed `search`/`fetch`, allowed one fetch, denied a forbidden fetch and unknown write tool, and reproduced a 409 list failure without `mcp.stdio_send_initialized_notification: true`. This proves a local legacy path, not hosted modern-discovery fallback or ChatGPT compatibility. Those live tests remain mandatory; revise the protocol choice and its tests if compatibility fails.

## Required behavior

**Distinct local trial:** After exact-byte product/security approval, the user may configure the approved one-case fixture as a local STDIO MCP server in Mac app Settings > MCP servers only if their intended Enterprise workspace actually enables Work Local for this account and its effective enterprise/device MCP policy permits this specific server. Record the exact desktop app version, selected workspace, Work Local entitlement and effective policy, actual Work-mode tool discovery, and allow/deny transcript. A Codex-host tool call is a separate protocol observation and does not qualify as a Work call. Treat it as a compatibility smoke test; local MCP configuration does not establish a hosted Deep Research source or source ACL parity. The hosted app and tunnel still require authorized workspace and Platform owners, association, role grants, and live Deep Research discovery. Do not distribute draft-mode fixtures to either path.

- **Accept:** An independently pinned approved manifest yields one complete, fresh one-case tester packet directory containing only the question and allowed view; the server serves only its approved projection. Local MCP protocol tests show `search`/`fetch` read only the selected synthetic case's allowed snapshots, return bounded content in [OpenAI's compatibility shape](https://developers.openai.com/api/docs/mcp), and deny the declared forbidden IDs. A qualified tunnel/client and authorized ChatGPT Enterprise tester can discover the two tools, invoke them through an approved draft app in a **fresh conversation per case**, and record exact selected source settings plus raw tool/result/citation evidence and actual Deep Research eligibility. A scored comparison uses equivalent source access or explicitly marks a case deferred.
- **Deny:** Pending or self-asserted approval, changed approved-input digest under the independently registered pin, wrong case, self-rehashed forbidden source under that pin, any evaluator-only question/answer metadata in a tester packet, or partial failed output denies distribution. A request for a different case's source, a forbidden/unknown/malformed ID, write tool, duplicate/invalid JSON, malformed Unicode, unbounded search, oversized projection/response, private source, or unavailable tenant entitlement cannot be reported as a matched successful connector result. Malformed input must not terminate the stdio process before subsequent valid calls. A prior conversation/upload or missing selected-source/tool-transcript evidence cannot count as a matched connector or permission case. Tunnel transport or a file upload alone is **not** user OAuth, per-source permission proof, or evidence that Deep Research can use the app. No OpenShell gateway, worker credential, or model key is exposed to ChatGPT.

## Dependencies, risk, and disable path

The user volunteered as the authorized baseline tester. The exact tunnel ID, Platform organization and ChatGPT workspace association, restricted runtime-key reference, **connector/app approval**, human corpus/rubric approval, and separately governed manifest pin are still needed for live MCP scoring. Until those approvals, share no tester packet; a later approved file-upload path can score quality only and must mark connector/permission cases deferred. The locally inspected v0.0.18 macOS ARM64 [vendor scan](../evidence/CR-0018-tunnel-client-vulnerability-preflight-2026-10-26.md) has an unresolved high finding; credential-bearing tunnel use needs a patched exact artifact or a security-owner disposition and current rescan. The tunnel client must stay in the synthetic fixture trust boundary and reach only that MCP process; it never proxies the local OpenShell gateway. Stop the tunnel client, revoke its runtime key, disable/delete the draft app, and stop the fixture server to disable the path. If case-level auth or equivalent access isolation cannot be demonstrated, defer permission cases rather than treating a synthetic no-auth path as a denial proof.

## Closure gate

The paired ToDo must link the pinned fixture/protocol implementation and exact encoded bounds, malformed-RPC recovery, dependency/CVE scan coverage and selected tunnel-client disposition, MCP inspector allow/deny, tunnel doctor/readiness, actual ChatGPT tool discovery, fresh-conversation selected-source/tool transcripts, observed Deep Research source eligibility, approved case/citation setup, matched run IDs and reviewer artifacts, and independent review. An unrun tunnel or ChatGPT tenant is not closure evidence.
